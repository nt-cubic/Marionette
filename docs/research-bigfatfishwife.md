## 0. 结论

BigFatFishWife 最值得借的不是人格文本、恋爱陪伴或生活模拟,而是它把「常驻 Agent 的连续感」
拆成了一套可恢复、可审计、可拦截的宿主机制:

1. 真实事件与模型叙述分离;
2. 固定事实、当前状态、历史日记和原始流水分层;
3. 时间由本地墙钟推进,模型不是时钟;
4. 未来承诺和到期动作有独立账本;
5. 「能做事」与「能打扰用户」是两道不同的闸门;
6. 自主程度、模型调用、工具轮数、墙钟时长和通知次数都有统一预算;
7. 空闲规划先算候选,永远允许「休息/不做事」;
8. 会话事件可以投影成稳定、可解释的员工状态;
9. 模型只能提出动作,Host 决定是否提交;
10. 客观事实不能被子模型或复盘文字改写。

dsh-room 进一步验证了一个适合 Marionette 的表现层原则:**一个活跃会话可以对应一个可见的
工作角色,角色状态完全由事件投影;任务是临时工作卡,不是新的员工。**

Marionette 不应该复制它的陪伴玩法,也不应该做 2.5D 办公室。值得借的是同一套
「人物在前、事实在后、状态可解释、预算可停止」的结构。

### 1.1 值得记录的具体参数

下列数值是参考实现的经验值,不是 Marionette 的最终契约。列出来是为了保留设计线索和失败边界:

这些数值不应进入员工人设让模型「记住」,而应作为 Host 常量、设置或测试夹具。

### 1.2 产品结构、数据面与执行/审批边界

**BigFatFishWife(BigFatWife)的结构**:

- 本地仓库没有一份根 README;入口是 `00-总览.md` 和 `03-架构设计.md`,配套 `04-部署手册.md`、
  `05-记忆系统设计.md`、`06-安全与运维.md`、`07-踩坑记录.md`,产品由 AstrBot 人格 + 多个插件
  组成(记忆、生活、闹钟、手机、浏览器、贴纸、邮箱、搜索、房间);
- 「常驻」来自 NAS 上的 AstrBot 容器、Telegram 长轮询和本地插件调度,不是 Marionette
  这样的桌面 Agent 宿主;模型、人格、记忆分居「大脑/家里/窗户/手脚」四层;
- 记忆数据不是一个数据库:原始消息流水、`pinned.md`、`state_current.md`、
  `state_history.md`、`journal/*.md`、`recall_state.json`、`last_raw.txt` 和插件流水
  各自承担一层;这支持「可检索、可回溯、可人工修正」,但也造成了大量文件格式和迁移成本;
- 生活引擎的 `state.json` 里还保存 `temporal`、`contact`、`budget`、照顾事实和活动;
  状态推进靠本地墙钟,模型只在检查点被调用;闹钟插件的固定文案目前硬禁用,到点只产生事件,
  面向用户的文字必须由模型生成。

| 参考模块 | 机制 | 可借鉴面 | 不照搬 |
|---|---|---|---|
| 记忆插件 | 原始流水、pinned/state/history、日记、召回索引 | 分层、增量、来源、只读快照、忘记与重建 | 伴侣日记口吻和长提示词 |
| 生活插件 | 本地 tick、预算、主动消息、工具循环、活动续段 | single-flight、预占、上限、journal 收尾 | 生活模拟、身体/精力/情绪循环 |
| 闹钟插件 | 固定时刻产生事件 | 事件与文案分离、到点幂等 | 固定问候文案直接出站 |
| 手机/搜索/浏览器 | 外部行动与信息获取 | 结构化结果、超时/截断、Host 安全边界 | 仅靠人格约束高风险点击 |
| 邮箱/语音/图片/贴纸 | 多模态出站 | 渠道独立闸门、资源大小上限 | 恋爱表达和角色素材 |
| 房间插件 | 把事件投影成可见角色状态 | 状态一瞥、外部状态优先、点击回到真实会话 | 2.5D 世界/家具/天气 |

**dsh-room 的结构**:

- README 明确同一套 RoomKit 跑在 DSH 插件、独立网页和透明桌面壳;`install/` 是验收分发快照,
  `release.json` 带版本和逐文件校验值,开发源码在 `dsh-room/` 与 `desktop/`;`docs/09–17`
  分别记录世界边界、阶段计划、首版契约、交接/同步、安装与桌面使用;
- 场景、家具、剧情和角色外观是版本化 JSON/内容包;场景操作可撤销、可导出/导入;
  角色行为通过统一动作接口被用户、剧情、外部工作状态或自主生活打断;
- 本地房间与桌面辅助窗通过单一家/所有权交接避免双写;网页试玩、DSH 和桌面的存档边界在
  README 里明确写出,不能把“同一份 UI”误读成“自动云同步”;
- Agent 工具默认关闭,由用户显式开启(`room_look`/`room_say`/`room_do` 才注册);没有模型时
  仍可换房、布置和手动互动,这是产品「不因模型不可用而整体失效」的降级原则;
- 内容包/场景/家具是带 schema 与校验错误的 JSON 数据,支持导入、导出和撤销;这提示员工模板、
  记忆导入也应做格式版本、大小上限和身份校验,而不是直接相信文件内容。

**任务执行与审批边界**:

- BigFatFishWife 的「任务执行」主要是生活 tick:同一时刻只跑一个循环,先在本地预算账本预占
  调用额度,再做模型请求;工具失败、模型失败和无结果都写回事实,不发送固定降级台词;
- dsh-room 不负责执行 DSH 任务,只观察会话事件并把六档状态投影给角色;它证明了「状态投影」
  可以与真正的执行器解耦,不能证明 dsh-room 有任务审批器;
- 参考项目没有成熟的「任务/计划/危险命令审批」协议。手机插件的支付、评论、系统设置等禁区
  主要靠人格与工具规则,不应被当成 Marionette 的权限模型;只有 dsh-room 的工具默认关闭和
  BigFatFishWife 的部分本地硬限制具备参考价值;
- Marionette 必须继续把真正的高风险动作交给现有 worker 权限卡和 Host 权限档;员工工具只能
  创建/查询/停止任务,不能新增 `task_approve` 或伪造审批结果。

### 1.3 当前 Marionette 对账摘要

截至 2026-11-17 工作树,员工模式已经不是空白草案:注册表、员工会话、侧栏员工组、状态投影、
任务工具、持久暂停、分层记忆存储、承诺账本、Telegram 绑定和 channel-neutral 通知闸门已经落地;
任务卡 Telegram 通知按稳定 staffId 找最新档案,员工会话重建不会回退绕过策略,辞退还会取消
活动/Proposed task 与 open/due commitments。任务预留、requestId 与并发检查已进入同一账本锁;
注册表级暂停会让新员工继承;员工/worker 的只读档、Computer Use schema 与 dispatch 都是 Host
硬门禁;普通通知冷却已持久化;task 终态自动写 journal,proposal 可 accept/reject。
但以下仍不能写成已完成:完整的持久通知审计与跨渠道矩阵、通用条件承诺、健康页、空闲候选规划、
精确 provider 模型调用计数与成本请求前预占、多员工多 Telegram chat,以及 E4 的长期常驻验收。
详细状态、偏差和待办见 [plan-employee-mode.md](./plan-employee-mode.md) §0.1、§6 和 §9。

## 2. 分层记忆

### 2.1 原始事件账本

参考实现先按天把双方消息追加写入 JSONL,每条带时间、角色、正文和渠道来源。整理程序按已消费
行数推进,只有新增消息才进入下一次总结。原始流水不因为模型遗忘或上下文压缩而消失。

值得借鉴:

- 原始事实 append-only;
- 整理游标与原始文件分离;
- 每轮整理只消费增量;
- 失败时保留原文和失败输出,不覆盖旧记忆;
- 日记正文带来源条数和日期脚注,以后能回溯是哪批事实生成的。

Marionette 映射:

- 不新增第二套 transcript。员工/worker 的会话事实仍来自 tee 和现有任务账本;
- 员工记忆只保存从 tee、任务账本或用户明确输入中提炼出的长期信息;
- 记忆条目带 sourceRefs,例如 sessionId、taskId、eventSeq、transcript 时间窗;
- 禁止把模型自己的汇报原句当成「已经发生」的证据。

### 2.2 固定事实单独存放

参考实现把姓名、身份、重要日期等长期事实放在 pinned 文件,不参加夜间状态的覆盖。整理提示词
明确规定固定事实是权威资料,不能因为本轮对话没提到就删除;新对话若与固定事实冲突,应放进
待确认,而不是直接改写。

值得借鉴:

- pinned 是人工或用户确认的稳定事实;
- 自动整理只能读 pinned,不能静默改 pinned;
- 冲突进入待确认队列;
- UI 必须明确区分「固定事实」和「模型推测」。

Marionette 映射:

- 偏好、硬边界、发布规则、命名习惯、用户明确否决过的方案进入 pinned;
- 模型只能提交 memory proposal;
- 只有用户确认或满足明确的 Host 规则,proposal 才能晋升为 pinned。

### 2.3 当前状态与状态历史

参考实现另存一份短小的 state_current,只保留关于用户、近期话题、待跟进和明天想聊的内容。
覆盖当前状态前,先把旧版本追加进 state_history。即使当前状态被模型写坏,历史快照仍在。

值得借鉴:

- 当前状态必须短,不承担全文记忆;
- 每次覆盖前留历史;
- 当前状态失败时 fail-open,不能阻塞主流程;
- 当前状态不是事实源,只是检索和提示词的快速入口。

Marionette 映射:

- state.md 只保留最近合作上下文、当前偏好的摘要、正在跟踪的事项;
- history.jsonl 保存每次修改的来源、前后摘要、操作者和时间;
- 任务完成/失败始终以任务账本为准,state.md 永远不能覆盖任务状态。

### 2.4 日记与任务复盘

参考实现按日期生成日记,并从生活流水里只取真实活动条目。系统标记、工具残骸和重复句会被过滤。
日记既有用于注入的简洁正文,也有原始来源脚注。

值得借鉴:

- 日记是模型可读的压缩层,不是唯一真相;
- 只根据真实事件生成;
- 同一内容去重;
- 工具调用残骸不直接进长期记忆;
- 长日记保留但注入时按窗口裁剪。

Marionette 映射:

- 员工日记以合作日或任务为粒度,记录目标、决策、产出、失败原因和用户偏好;
- 原始 worker 工具轨迹仍保存在会话/tee,日记只存压缩结果;
- 不把「正在思考」「正在运行」之类瞬时状态写进记忆;
- 自动复盘失败不影响任务完成记录。

### 2.5 原子写

参考实现先写临时文件,再使用原子替换,避免断电留下半截记忆。结构化进度文件也走同样路径。

Marionette 映射:

- staff registry、policy、commitments 和 memory index 都沿用 chief store 的原子写;
- 内容文件与索引更新应有明确顺序;
- 索引失败可从目录扫描重建;
- 不得用「覆盖整个目录」作为日常更新方式。

### 2.6 记忆分层与召回

参考实现不使用向量优先,而是:

- 最近 7 天日记整篇注入;
- 7 至 60 天只取概要;
- 60 天以上默认不注入,但全文仍可搜索;
- 用户明确问旧事时再翻对应日期;
- 固定事实、当前状态、近期日记分别有独立预算;
- 超预算时先减少近期日记,不先丢固定事实。

此外提供过本地小型向量索引作为后续方案,但当前主路径仍是「近期全文 + 旧日记按需检索」。

Marionette 映射:

- 第一阶段只做 pinned/state/journal 三级加全文检索;
- 向量 RAG 继续后置;
- 每次记忆注入有总字符预算和分层预算;
- 固定事实不可被裁剪;
- 记忆没找到时表述为「没找到」,不能说「从未发生」。

### 2.7 注入优先级

参考实现在聊天请求里明确加入当前时间、当前用户消息、当前图片和当前任务事实,并声明旧日记、
旧回复和压缩摘要不能覆盖当前用户事实。生活轮还会注入用户明确说过的照顾状态,没有明确事实
时不制造需要。

值得借鉴:

- 当前用户指令优先于历史偏好;
- 最新任务事件优先于旧总结;
- 记忆只作背景,不能压过当前事实;
- 无事实时不生成建议或任务。

Marionette 映射:

员工 bootstrap 和每轮上下文都应有明确优先级:

~~~text
Host 硬策略
> 当前用户消息 / 当前审批
> 任务账本最新状态
> pinned 事实
> 当前 state
> 历史日记
> 模型推断
~~~

### 2.8 记忆页与可检视性

参考实现生成只读记忆页,展示固定事实、经验、当前状态、最近日记和活动流水。页面不会反向写入记忆。

Marionette 映射:

- 员工档案页提供只读总览和明确的编辑/删除动作;
- 显示来源、更新时间、作用域和状态;
- 「清空记忆」是独立危险操作;
- 删除后不得在下次同步或整理时自动补回;需要 tombstone 或删除账本。

### 2.9 记忆卫生与反馈回路

参考实现入库前剥离图形 emoji,避免模型偶然的一次用法被反复读入后固化成永久口吻;输出前还会
剥掉 DSML/tool-call 语法残片。它还有纯本地 replay guard:长回复(至少约 120 字)与历史回复
归一化后相似度约 0.92 以上、或一段是另一段完整子串时,视为复刻旧回复;连续“字、字”式病理性
口吃达到约 6 处时才拦截,避免误伤正常停顿。

还区分活动流水、梦、决定等不同 kind,避免非事实内容被当成真实活动。

值得借鉴的不是 emoji 本身,而是原则:**模型生成物重新进入上下文前必须清洗,避免自我模仿和
错误强化。**

Marionette 映射:

- 不把工具状态栏、调试文本、临时进度、UI 标签写进记忆;
- 不把员工自己的汇报自动当成用户偏好;
- 连续重复的通知/摘要要有去重和冷却;
- 自动摘要保留来源,模型推断标记为推断。
- 对重复回复、工具语法泄漏、异常重复语做本地检测;检测失败时只记录/重试,不把坏文本入库。

## 3. 纯本地时间线与未来承诺

### 3.1 时钟不调用模型

参考实现用本地函数推进墙钟,维护当前活动、开始时间、预计结束、已过时长、跨天/时段事件和最近
时间事实。模型只在真正需要决定时被调用。

关键行为:

- 系统时钟回拨时不倒放状态;
- 同一 due 事件只产生一次;
- 重启后能从持久化状态恢复进行中的活动;
- 聊天、心跳和启动恢复可以重复调用 advance,但不会重复记同一事件;
- 当前活动超时只记事实,不替模型生成给用户看的话。

Marionette 映射:

- 员工状态推进必须是纯本地投影;
- worker 的 running/waiting/stale 由事件时间计算;
- 「多久没进展」「什么时候开始等用户」「离 deadline 多久」都是 Host 事实;
- 不为了刷新状态每分钟调用模型;
- 到期事件应有幂等 id 或 event key。

### 3.2 活动与任务边界

参考实现允许任意自然语言活动名称,预计时长只是默认值,不是硬截止。结束后记录实际耗时和结束原因。
自然语言推断只作为工具未调用时的兜底,不是主要协议。

Marionette 映射:

- 主要协议是 task_start/task_status 等结构化工具,不做正则驱动编排;
- 员工自己直接执行的工作也可以建立轻量 activity/phase;
- 预计时长与硬超时要分开;
- 超时只标 overdue,是否取消由策略和用户决定。

### 3.3 承诺账本

参考实现把「答应过但没兑现的事」放在独立 promises 列表中,并在聊天、生活轮和睡眠整理时注入。
到点事项另有 alarms,闹钟触发时不受普通静默限制。它还尝试从自然语言推断用户要求或角色承诺,
但没有把推断当成唯一入口。

值得借鉴:

- 承诺与任务分开;
- 承诺有正文、期限、来源、状态和完成时间;
- 兑现后写回,避免反复提醒;
- 到期唤醒员工,由员工决定如何接住;
- 用户主动恢复、早安、闹钟等事件可以越过普通静默;
- 自然语言推断只是辅助,关键承诺应有结构化工具和可见 UI。

Marionette 映射:

新增 commitment ledger,至少包含:

~~~jsonc
{
  "commitmentId": "cmt_...",
  "staffId": "staff_...",
  "text": "CI 通过后继续合并",
  "kind": "follow_up | reminder | promise | condition",
  "dueAt": 0,
  "condition": "ci_green",
  "sourceRef": "session:.../event:...",
  "status": "open | due | done | cancelled | expired",
  "createdAt": 0,
  "completedAt": 0
}
~~~

任务完成不等于承诺完成。例如「修好」是 task,「修好后告诉我并等我确认合并」是 commitment。

### 3.4 执行循环、续段与停止

参考生活引擎把一轮执行拆成可审计的有限循环:

- `tick` 同一时间只允许一个在途;重复触发直接跳过,避免后台线程互相叠模型调用;
- 每轮工具轮数只接受 `1..8`,墙钟只接受 `30..900` 秒;到线后进入收尾,不继续无限调工具;
- 普通工具 60 秒超时,画画单独给 200 秒;工具返回内容截到约 3500 字,防止一次工具输出撑爆上下文;
- 想继续做同一件事时显式 `keep_playing`:每段 2–45 分钟,同一会话最多 10 段或约 2 小时;
  续段保留上一段上下文和进度,超过上限后只能正常 journal 收尾;
- 工具失败仍是结构化 tool result;模型调用失败或没有可用 provider 时只记录暂停原因,不发送
  “我先去做啦”之类固定台词;
- 只有真正调用工具的工作会消耗生活精力;发呆或只写 journal 不扣预算,防止为了展示忙而制造活动。

Marionette 映射:

- 用 task 状态机 + worker turn/墙钟 cap + `task_send/task_resume` 表达有限续段;
- resume/续段要带同一 taskId、累计 turn、累计成本和来源,不能伪装成新任务;
- 到线只允许收尾/交付/写复盘,不允许模型自行延长;
- 自动规划同一员工单在途;用户明确请求可以抢占普通后台规划;
- 工具失败、超时、无模型和策略拦截都进入可解释的任务/通知状态,不要用固定台词掩盖。

## 4. 主动出站与打扰闸门

### 4.1 两道闸门

参考实现明确区分:

- 第一道:是否允许 Agent 自主做事;
- 第二道:是否允许它主动打扰用户。

后台做事、写日记、准备草稿可以继续,但向用户发消息、语音、图片或邮件必须单独通过第二道。

Marionette 映射:

- staff 可以继续 worker;
- 汇报、桌面通知、Telegram 和邮件是独立出站能力;
- waiting_user 是任务状态,不等于已经成功通知;
- 每个出站动作都要有 channel、policy decision 和审计记录。

### 4.2 只使用明确事实

参考实现从用户明确话语中维护工作/睡觉/勿扰/吃饭/疲劳等状态。没有明确事实时不推测;状态有保险
期限;用户说「下班了」「吃过了」「好多了」会解除对应状态;已采取动作有冷却,避免反复催。

Marionette 不复制健康提醒,但应复制结构:

- 用户明确说「开会」「深度工作」「不要通知」「等我确认」才进入 DND;
- 沉默本身不推断用户忙碌或生气;
- DND 有到期时间和显式恢复词;
- 已汇报过的事项进入冷却,避免重复。

### 4.3 本地心跳与模型分工

参考实现本地心跳只负责判断「到点看一看」,是否发消息和下次何时再看由模型决定。Host 仍提供硬门禁:

- 夜间静默;
- 最近刚聊过则不另发;
- 刚主动发过则有冷却;
- 连续多条未回复后停止追发;
- 闹钟/早安有明确例外;
- 模型失败或返回空时不降级成固定台词;
- 全局出站禁用标志会拦住所有主动媒体和文字;
- stop/start 命令切换暂停状态。

Marionette 映射:

- 通知必须由事件触发,不允许「到点必须说点什么」;
- 完成任务、失败、等待授权、承诺到期可以作为触发事实;
- 普通 running 状态不产生周期性消息;
- 用户没有回应不是追发理由;
- 生成失败时宁可不发,不能发送日志式 fallback;
- 急停必须持久化到 Host,而不是只在内存里暂停;
- 恢复需要用户明确操作。

### 4.4 优先级例外

参考实现允许闹钟、早安等越过夜间或其他普通静默。Marionette 应定义有限例外:

- waiting_user 且用户仍需授权;
- 任务失败且阻塞后续工作;
- 用户设置的一次性提醒;
- 用户明确要求到期通知;
- 安全/权限事件。

例外必须写进策略并在 UI 可见,不能由模型自己宣布「这条很紧急」。

### 4.5 降噪、抑制与事实落账

参考实现把「没发出去」也当成需要记录的结果:

- 全局主动出站开关关闭时,工具返回明确拒绝,并把想说的内容写进日记,而不是假装成功;
- 刚聊过 8 分钟内不另发;连续 2 条没有回复就先停发(心跳层更保守地到 4 条);
- 深夜 00:30–08:30、明确工作/勿扰、会话已道晚安等条件分别有原因和退出方式;
- 用户说“已经好了/吃了/醒了/下班了”等恢复词会解除对应事实,不靠沉默猜测;
- 主动消息成功后才记 contact ledger;重复事件、同一进度和相同错误必须合并/冷却;
- 没有 provider 时不发固定 fallback;闹钟固定文案也已硬禁用,只允许事件进入模型;
- 诊断要能显示下一次心跳、今天看了几次/发了几次、未回复计数和当前静默原因。

Marionette 当前实现已完成 channel-neutral 通知闸门、桌面/Telegram 渠道分离、优先级例外、
持久暂停和 Telegram 绑定;Telegram 任务卡按稳定 staffId 取最新档案。仍待补的是持久通知账本、
跨渠道抑制原因 UI 和完整端到端验收。不能把 `verify-staff-status` 的纯函数测试当成端到端通知验收。

## 5. 中央策略、预算与循环保护

### 5.1 模式投影

参考实现用 economy/normal/full 三档一次覆盖整套配置:是否允许后台模型、主动联系、每日消息数、
工具轮数、墙钟时长、上下文条数、主动媒体和邮件权限。这样切换模式时不会漏改散落开关。

Marionette 映射:

员工应有单一 StaffPolicy,而不是多个页面各存一部分。建议至少包含:

~~~jsonc
{
  "autonomy": "manual | assisted | autonomous",
  "allowedProjects": [],
  "maxActiveTasks": 1,
  "maxTurnsPerTask": 30,
  "maxWallMinutesPerTask": 120,
  "maxModelCallsPerTask": 0,
  "maxCostPerTaskUsd": 0,
  "maxReportsPerHour": 4,
  "notificationCooldownMinutes": 30,
  "quietHours": "23:00-08:00",
  "allowBackgroundWork": true,
  "allowTelegram": false,
  "pausedUntilUserResumes": false
}
~~~

字段只是设计起点,最终以产品和 agent 能力为准。关键是所有出站和执行入口读取同一份策略。

### 5.2 调用前预占预算

参考实现在向模型发请求前先占用一次调用额度,而不是请求完成后才记账;持久化失败时宁愿跳过请求。

Marionette 映射:

- task_start 时预占并发槽;
- 每次模型/turn 调用前预占 turn 或成本预算;
- 超预算进入 paused/budget_exhausted,不是静默无限继续;
- 重启后预算不能清零;
- 用户提高预算后可恢复。

### 5.3 短期速率异常

参考实现除每日额度外还有一个短窗口模型调用上限,用于识别循环或配置错误。

Marionette 映射:

- 每秒/每分钟事件速率;
- 连续相同工具调用;
- 连续无文件/状态变化的 turn;
- 连续重复汇报文本;
- 同一 task 重复失败;
- worker 启动/退出抖动。

达到阈值时先暂停新增工作并生成诊断,不要直接杀所有任务。

### 5.4 墙钟与工具轮双上限

参考实现同时限制模型工具回合数和墙钟时长。到达上限后进入收尾阶段,只允许写日记/续段等有限动作。

Marionette 映射:

- 每个 task 有 turn cap 和 wall-clock cap;
- 接近上限时给 worker 一个受控收尾提示;
- 收尾阶段限制可用工具;
- 超时状态明确为 timed_out,不能伪装 completed;
- 用户可显式续期,续期形成审计事件。

### 5.5 成本与健康可见

参考实现有模型价格、用量曲线、首字延迟、健康检查和看门狗。Marionette 不需要照搬页面,但应借:

- 员工页显示任务数、今日调用、预计成本、最后活动、最后汇报;
- Host 诊断显示 ledger 可写、Telegram 是否在线、worker 是否卡住、记忆是否可写;
- 预算耗尽、审批等待、通知被抑制都应有可解释状态。

## 6. 空闲规划与「不做事」

参考实现用纯规则给候选行动打分:

- 未完成项目基础分高;
- 项目当天轮数达到上限后大幅扣分;
- 连续记录同一份进度视为卡住并扣分;
- 探索、小窝、休息是固定候选;
- 分数不足时真正休息;
- 模型仍能否决默认方向,但不会面对完全空白的选择。

Marionette 映射:

员工空闲规划只允许来自有据可查的候选:

1. due commitments;
2. 用户批准的 backlog;
3. 失败任务的重试条件已满足;
4. 等待外部条件且刚刚满足;
5. 用户明确要求定期检查的事项;
6. no-op/待机。

不得把「找点事做」「展示主动性」当成工作。重复同一计划、同日多次尝试同一失败方案、没有新证据时
再次唤醒,都应扣分或直接禁止。

## 7. 状态投影与车间可视化

### 7.1 事件到状态

dsh-room 把会话事件压成六档:

- turn/start -> thinking;
- tool/call -> working,询问用户时 -> waiting;
- tool/result -> result;
- approval/asked -> waiting;
- turn/end -> success/error/waiting/空闲;
- 中止等未知终态回空闲,避免卡在上一档。

聚合优先级为 waiting > error > working > thinking > result > success。

参考实现还有:

- success/error 短时后自动消失;
- 其他状态长时间无事件视为 stale;
- 同一会话按最新事件更新;
- 多会话汇总时选优先级最高、同优先级取最近者;
- 任务文字取最后一个 in_progress,没有则取第一个 pending;
- 长任务按码点截断,避免切坏字符。

Marionette 映射:

员工行不应仅显示员工主会话状态,而要聚合其任务和 worker;Marionette 当前实现把
`failed` 与可恢复的 `interrupted` 分开:

~~~text
waiting_user > failed/interrupted > running > thinking > idle
~~~

可附加:

- 最需要用户注意的 task;
- 当前 worker 标题;
- 最后事件时间;
- 是否因 DND 暂缓通知。

终态保留时长由产品决定,不要机械照搬 8 秒;但必须有衰减,避免员工永远庆祝或报错。

### 7.2 一个会话一个临时工作角色

dsh-room 将一个活跃会话映射成房间里的临时角色,状态驱动它去书桌、等待、庆祝或报错。临时角色
不进存档;主角色才是长期人物。

Marionette 应采用同一信息结构,但不做房间:

- 员工 = 长期人物;
- worker/task = 车间工作卡;
- 卡片状态由事件投影;
- 点击卡片回到真实 worker 会话;
- 删除任务卡不删除员工;
- worker 不进员工注册表。

### 7.3 外部状态优先于自主行为

dsh-room 的行为循环优先级是:外部命令队列 > 被用户/剧情占用 > 外部工作状态 > 自主生活。

Marionette 映射:

~~~text
用户直接消息/审批
> 当前 worker 阻塞事件
> due commitment
> 已批准后台任务
> 空闲规划/待机
~~~

模型不能因为「员工想主动做点事」而压过用户当前指令。

### 7.4 视觉边界

Marionette 的员工组和车间继续使用现有侧栏/任务卡语言。不要引入 2.5D 房间、Live2D、
家具、天气或独立游戏化设计系统。

可借鉴的是:

- 状态一瞥可见;
- 等待用户比正在工作更醒目;
- 错误不会无声消失;
- 点击状态进入对应事实;
- 长期人物和临时任务层级清楚。

### 7.5 UI 操作细节

参考实现值得抄的是信息层级和操作路径,不是房间外观:

- 状态页把当前任务、等待原因、最后事件和连接是否收到事件分开显示;有事件计数就能判断
  “监听失效”与“真的没有工作”;
- 状态卡只显示最新 in_progress 任务,没有就显示第一个 pending;完成/失败短暂保留后回空闲;
- 连接页提供只读环境/引擎/会话事件/工具开关诊断,并有“模拟一次工作状态”按钮,可单独验收
  UI 联动而不启动真任务;
- dsh-room 的记忆支持查看、逐人忘记、清空、导出和导入;BigFatFishWife 的记忆页明确标注
  “只读快照、不写回”;两种做法共同说明“可检视”和“可修改”应是不同权限动作;
- 没有模型时仍展示手动模式;工具开关默认关闭,打开后才注册工具;失败显示可重试操作而不是
  卡在“正在加载”;
- 移动端/窄窗口不是把桌面卡硬缩,而是按容器宽度改单列;Marionette 沿用现有 3px 视觉语言。

员工模式的对应落点:

- 员工行一瞥显示状态和主任务,右栏显示任务、记忆、承诺和预算;
- 诊断显示 scheduler、heartbeat、worker、ledger、memory、Telegram 和通知抑制原因;
- 记忆/承诺的查看、编辑、完成、删除、清空分别是明确动作,危险动作二次确认;
- 提供受控模拟/测试入口,但模拟状态必须有醒目标记且不能写入业务账本。

## 8. 模型动作、事实与主观总结

### 8.1 结构化动作白名单

dsh-room 的主人侧适配器要求模型输出有限动作:

- move;
- interact;
- say;
- emote;
- none。

动作参数会再次清洗;场景和他人发言被视为不可信数据;只有 Host 提交的事件能改变事实。

Marionette 映射:

- 员工控制工具继续使用结构化 schema;
- 模型输出不能直接写 staff registry、policy、pinned memory;
- worker 结果、网页、仓库文本都是不可信输入;
- 需要改变状态时必须经 Host 校验和 idempotency 检查。

### 8.2 单在途、超时、取消和退避

参考适配器限制同一时间只跑一个生成请求,有 45 秒超时、小时额度和指数退避。取消后迟到结果被丢弃。

Marionette 映射:

- 每个 staff 的自动规划/复盘同一时间只跑一个;
- 取消或策略变化后,迟到结果不得提交到新任务;
- 使用 requestId 或 token 校验结果代次;
- 连续失败退避,但用户直接消息可优先恢复;
- 预算按请求前占位。

### 8.3 客观事实与个人复盘分离

dsh-room 的 ExperienceStore 把已提交事件保存为 facts,把模型生成的 reflection 单独保存。
摘要失败仍保留事实,可重试;完成身份和参与者不能被摘要改写。删除有 tombstone,重连不会把已删除
经历自动补回。

Marionette 映射:

- task ledger / events 是 objective facts;
- worker report、staff journal、reflection 是派生文本;
- 派生文本带 sourceRefs 和 status;
- 摘要失败时任务仍完成;
- 用户删除记忆或复盘后保留删除标记,防止自动补回。

### 8.4 共享场次协议的可借鉴部分

dsh-room 的世界场次使用 requestId、epoch、seq、快照与重放解决重复提交、旧控制权和断线恢复。
Marionette 已有任务幂等、事件账本、interrupted/resume,不需要照搬整套世界协议。

只保留以下原则:

- 事实写入必须幂等;
- 旧代次结果不得写回;
- 事件序号单调;
- 缺口通过快照/回放恢复;
- 客户端动画或本地 UI 状态不能成为共享事实源。

## 9. 安全边界

### 9.1 可借鉴的硬校验

参考项目的浏览器服务做了真实的结构性防护:

- 必须有内部 token;
- 只允许 http/https;
- 只允许 80/443;
- 拒绝 localhost、.local、.internal;
- 拒绝解析到私网、回环、链路本地和保留地址;
- 页面子请求和跳转逐个检查,防止公网 302 到内网;
- 正文和截图有大小上限。

Marionette 的员工浏览器/Computer Use 必须继续使用现有的 Host 授权和 WebView 边界,不能只靠提示词。

### 9.2 不应照搬:提示词式高风险权限

参考项目的手机插件虽然没有单独的购买/评论 API,但具备通用点击、滑动和输入能力。支付、评论、
陌生人私信、系统设置等禁区主要靠人格提示词约束,不是结构化意图门禁。

Marionette 映射:

- 高风险动作由 Host 识别并走审批;
- 权限档位必须对应不同的执行路径,不能只是追加一句提示词;
- 员工不能修改自己拥有的项目白名单、预算、审批策略或技能;
- 网页、worker 输出和用户仓库中的文本不能提升权限。

## 10. 运维与数据生命周期

参考项目值得借的运维原则:

- 原始数据和派生数据分开备份;
- 配置、记忆、会话和任务账本是恢复核心;
- SQLite 一致性备份前停止写入或使用安全快照方式;
- 定时任务失败要重试;
- 备份恢复要演练;
- 服务/容器重启后自动恢复;
- 看门狗区分未运行、卡住和无响应;
- 成本、余额和错误集中体检。

具体实现里还有几项适合直接变成验收项:

- BigFatFishWife 每日 04:30 本地备份、保留 14 天;另有每月拉取到 Windows 的异机副本、
  保留约 6 份;备份时先停写入容器,无论失败都尝试把服务拉起来;
- 恢复不是只写文档:要实际解包、重启、检查旧对话/日记仍可读;备份日志要有时间和产物大小;
- 诊断页分别报告引擎、DSH 会话事件、模型能力、Agent 工具、最近事件时间和连接降级原因;
  “已连接但没有事件”与“连接失败”不能合并成一个绿灯;
- dsh-room 首次下载桌面辅助组件时显示进度、允许取消/重试,缓存后续复用;发布分发快照和
  `release.json` 有逐文件校验,降低“源码/安装包不是同一版”的错觉;
- 运维文档明确写入许可证、凭据位置、备份排除项和恢复路径;敏感凭据不能进入员工记忆、
  诊断摘要或通知正文;
- BigFatFishWife 的运维把管理面板/QQ WebUI 限制在内网、默认零公网端口映射;API key 留宿主
  配置而不是人格/记忆,并给 key 设月度限额;容器用 `restart: unless-stopped`,定时任务失败要
  重试,DSM 升级后还要复查 `/etc/crontab` 是否被系统重置;
- 对 Marionette 而言,员工注册表/策略、commitments、memory index/正文、task/event 账本和
  tee 必须同属一份可恢复快照;恢复后先核对 ledger 再启动自动唤醒,不能重放已完成任务。

Marionette 映射:

- staff registry、policy、commitments 和 memory 应随现有 Marionette 数据目录备份;
- task/event 账本恢复优先于员工聊天文本;
- 恢复后先核对账本,再启动自动跟进;
- 不要让员工在恢复过程中自动重放已完成的 worker;
- 健康页至少显示 scheduler、telegram、ledger、memory、worker 和预算状态。

## 11. 具体的 Marionette 员工模型建议

### 11.1 员工不再是三项,而是六项稳定资产加两项派生视图

稳定资产:

1. 持久会话;
2. 员工档案;
3. 控制工具;
4. 分层记忆;
5. 承诺账本;
6. Host 强制策略。

派生视图:

1. 员工状态投影;
2. 员工/任务汇报文本。

### 11.2 建议目录

~~~text
~/.marionette/chief/
  staff.json
  tasks.json
  events.jsonl
  commitments.json
  memory/
    <staffId>/
      pinned.md
      state.md
      history.jsonl
      journal/
        YYYY-MM-DD.md
      index.json
      proposals.jsonl
~~~

目录名只是建议。关键约束是固定事实、当前状态、历史、原始事实和承诺彼此分开。

### 11.3 建议工具扩展

chief-m0 历史基线是 10 个控制工具;当前工作树已经把员工扩展接到
`src-tauri/src/chief/tools.rs`,总计 16 个:

- memory_recall:读取本员工的分层记忆;
- memory_propose:提交候选偏好/经验,不能直接改 pinned;
- memory_forget:是否开放给员工需谨慎;默认只允许用户 UI 操作;
- commitment_add:建立未来跟进/提醒/条件承诺;
- commitment_list:查询未完成承诺;
- commitment_complete:兑现或取消;
- staff_status:查询自己的 task、budget、notification gates 和 waiting 原因。

此外现有工具仍包括 `task_resume`,用于恢复 `interrupted` 任务;没有 `task_approve`
或任何修改员工档案/策略/白名单的工具。

工具只对本 staffId 生效。员工不能查其他员工的私有记忆,除非未来明确设计团队共享知识库。

### 11.4 建议状态投影

~~~jsonc
{
  "staffId": "staff_...",
  "displayState": "waiting_user | failed | interrupted | running | thinking | idle",
  "activeTaskId": "task_...",
  "waitingReason": "permission | question | plan_approval | user_input | null",
  "lastEventAt": 0,
  "lastProgressAt": 0,
  "lastReportAt": 0,
  "taskCounts": {
    "running": 1,
    "waitingUser": 1,
    "failed": 0
  },
  "notification": {
    "suppressed": true,
    "reason": "quiet_hours"
  }
}
~~~

该对象是投影,不单独成为可写事实源。

### 11.5 建议通知矩阵

~~~text
事件                    默认行为
task completed          立即或合并汇报
task failed             立即汇报,附失败阶段和证据
waiting_user            立即提示,但同一任务去重
commitment due          立即提示
ordinary progress       默认不通知
same error repeated     合并/冷却
quiet hours             除用户指定例外外延迟
stop all/pause          所有非安全通知立即停止
~~~

当前工作树:优先级事件能绕过勿扰/冷却,`allowTelegram` 只由 Telegram 渠道检查,桌面通知走
channel-neutral gate;前端纯函数的优先级表已与 Rust 对齐(`interrupted/permission/question/plan`
在内);普通通知的冷却与小时额度已持久写员工档案,写盘失败 fail-closed。仍真实存在的缺口是
桌面/Telegram 共用一份普通频率额度、没有邮件/媒体通道、持久抑制审计和完整 UI。设计目标不能
替代这些实现缺口。

## 13. 明确不借

### 13.1 代码结构

- 不用正则承担关键任务状态、权限或承诺创建;
- 不让自然语言推断覆盖结构化账本;
- 不让模型直接修改 policy、pinned、员工注册表或审批结果;
- 不用提示词代替 Host 权限门禁。

- 不复制恋爱/伴侣人格和角色扮演目标;

- 不做员工市场、群聊角色扮演或社交广场。

- 第一版不上向量 RAG;
- 不做另一套会话数据库;
- 不做通用世界协议和多人同步;
- 不把每个 worker 变成永久员工;
- 不为状态动画增加独立事实源;

## 15. 最终判断

这套参考项目提供的最大灵感不是「让 Agent 更像人」,而是让用户随时能回答五个问题:

1. 它现在在做什么?
2. 它为什么停下来?
3. 它答应过我什么?
4. 它凭什么说自己记得/完成了?
5. 我能在哪里停止、修改或忘记?

Marionette 员工模式只要把这五个问题做成 Host 可兑现的事实,就会比多数只有聊天皮肤和人格提示词的
Agent 产品更可靠。
