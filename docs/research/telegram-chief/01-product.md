# 产品定义：Marionette Chief

## 1. 用户到底想买什么

用户要的不是“用 Telegram 发指令给某个预先选中的 Agent”，也不是“把桌面 UI 做一套命令快捷方式”。
用户要的是：

> 我的电脑在运行，我离开家以后，仍然可以像给一位可靠同事发消息一样，把目标交出去；
> 对方知道我的项目和工具，会自己安排合适的 Agent 去做，遇到真正需要我拍板的事情才回来问，
> 做完把结果交给我。

因此，Telegram 只是远程对话面。产品本体是下面四件事的组合：

1. **持续存在的 Chief**：它记得用户偏好、当前优先级和过去任务；
2. **可执行的本地环境**：项目、ACP Agent、浏览器、Computer Use、命令和网络；
3. **有状态的任务系统**：任务可以被启动、观察、追问、停止、恢复和交付；
4. **Host 持有的安全边界**：Chief 很能干，但不能给自己扩权。

## 2. 与现有“远程桥”的区别

| 维度 | 现有 Telegram 桥 | Marionette Chief |
|---|---|---|
| 产品隐喻 | 多会话遥控器 / 呼叫器 | 远程首席助理 |
| 用户先选谁 | 用户切换会话或引用某条通知 | 用户只对 Chief 说目标 |
| 谁决定项目与 Agent | 用户 | Chief 在 Host 允许的范围内决定 |
| Telegram 消息去向 | 最近活跃会话或被引用会话 | 固定进入同一个 Chief 会话 |
| 工作线程 | 原会话本身 | Chief 通过控制 MCP 创建普通 worker |
| 多会话噪声 | 每个会话各自推送 | Host 聚合，Chief 给统一结论 |
| 命令 | `/new`、`/model`、`/status` 参与主要操作 | 自然语言为主；斜杠只保留少量安全逃生口 |

现有桥不是废弃对象。它是 Chief 的底层能力来源，也可以继续作为高级用户的“直接控制模式”。

## 3. 目标用户与部署形态

第一版面向 **单机、单 owner**：

- 一台 Windows 电脑；
- 一个 Marionette 安装；
- 一个已配对 Telegram 私聊；
- 用户拥有本机项目和 Agent 的登录 / 订阅 / API key；
- 同一时间只有一个本地用户把电脑用于交互，Chief 与本地 UI 可以同时在跑。

“每个人配一个自己的 Bot”指每个用户在自己的电脑上配置自己的 Telegram bot、Chief Agent 和
provider。它不是云端多租户 SaaS，也不是一个 bot token 服务所有人。

## 4. 典型场景

### 4.1 远程修代码

用户在手机上发：

> Marionette 今天构建是不是挂了？看一下，修好以后把验证跑完。别发布。

Chief 应当：

- 在允许项目里识别 Marionette；
- 查询最近任务 / 构建信息，决定是否需要新 worker；
- 用现有 Agent 和项目上下文复现；
- 需要执行高风险命令时把审批卡发回 Telegram；
- 完成后报告根因、改动文件、测试结果和仍存风险；
- 不执行发布、签名、上传 Release 或重启线上实例。

### 4.2 远程接力一个正在跑的任务

用户发：

> 刚才那个数据库迁移任务到哪一步了？先别继续写，等我确认。

Chief 应当查询任务状态并停止或暂停 worker；不能靠“猜最近会话”误操作别的项目。

### 4.3 浏览器研究与资料整理

用户发：

> 查一下这三个库最近的维护情况和许可证，整理成对比，源码放进 Marionette 的调研目录。

Chief 可选择一个 read-only 调研 worker；需要浏览器控制时按现有浏览器授权模型请求批准；
最终交付表格、来源链接和写入的文件路径。

### 4.4 让 AI 改 Marionette 自己

用户发：

> 把 Telegram 状态栏的错别字修掉，跑现有回归。先给我 diff。

这应当被支持，但默认遵守自我修改保护：

- 在独立 worktree / branch 上做；
- 可以构建与测试；
- 不自动 commit 到主分支、不 push、不发布、不自动重启当前 Marionette；
- 最终 diff、测试结果和合并建议交给用户。

### 4.5 日常电脑任务

用户发：

> 把今天下载目录里的发票按月份整理，文件名保留原编号。

这不是代码任务，可能需要普通文件会话或 Computer Use。第一版可以支持**已授权项目 / 已共享窗口**
内的操作；任意新增目录、整盘访问和新的窗口共享仍属于本地确认，避免“手机一句话开放整台电脑”。

## 5. 首次配置

配置流程应当像“雇一个助理”，不是填写一张运维表单：

1. 用户沿用现有 Telegram 配对，确认唯一 chat / owner。
2. 选择 Chief 使用的 ACP Agent。
3. 选择模型与提供商绑定，或沿用该 Agent 当前默认。
4. 选择一个或多个“允许 Chief 调度”的项目。
5. 为每个项目选择默认 worker Agent、模型和权限档位。
6. 设置并发上限、是否允许远程批准、是否允许写文件。
7. 做一次连通性测试：手机发一句自然语言，Chief 回复并成功查询项目列表。
8. 生成可见的 Chief 会话；以后本地 UI 与 Telegram 打开的是同一段对话。

建议首屏只给三个概念：**Chief 是谁、它能碰哪些项目、遇到危险时谁说了算**。高级参数折叠，不把
所有 ACP 能力、MCP 插件和工具开关堆到首次配置里。

## 6. 自然语言体验

### 6.1 用户不需要知道路由细节

下面两种输入都应成立：

> 帮我修一下最近那个登录问题。

> 用 Codex 在 Marionette 项目里修登录，写测试，别推送。

第一句由 Chief 根据最近工作、项目描述和用户偏好判断；第二句只是给 Chief 更强的显式约束，
不是给 Host 的命令语法。

### 6.2 Chief 应在什么时候提问

只在会实质改变结果时问，例如：

- 两个同名项目，无法安全判断；
- 用户说“上线”但没有说明目标环境；
- worker 返回两个互斥方案，且用户偏好未知；
- 需要危险命令、额外目录、凭据或新权限；
- 成本可能显著超出配置预算。

不应问：

- “请问要调用哪个 MCP 工具？”
- “请选择 session id”
- “请回复 /start_task”；
- Host 能可靠推断且风险低的细节。

### 6.3 默认交流形态

Telegram 中的主对话始终来自 Chief。Host 可以发送确定性状态卡，但文案应保持少而明确：

- “已交给 [项目 / Agent] 开始处理。”
- “在等你批准：要执行 …；影响范围 …。”
- “任务完成：改了 3 个文件，验证通过。要看详情回复‘贴出 diff’。”
- “任务失败：测试 2 失败，worker 已停止。原因摘要 …。”

原始长日志、完整 command output 和每一条 thought 不直接刷进私聊；可按需展开或作为附件交付。

### 6.4 快速操作仍然需要

自然语言是主路径，但保留少数确定性逃生口是合理的：

- 停止全部任务；
- 查看所有任务；
- 重新连接 / 状态；
- 帮助与配对。

它们是安全和控制入口，不是完成主工作流的必经命令。

## 7. 产品原则

1. **目标优先于命令**：用户描述结果，Chief 负责编排。
2. **同一段 Chief 对话**：手机与桌面不产生两份人格、记忆和上下文。
3. **worker 必须可见**：任何真正写文件、跑命令、开浏览器的会话都能在本地 UI 找到。
4. **异步且可恢复**：长任务不能依赖“这一轮 HTTP 请求还没断”。
5. **请示只在判断点**：可继续的工作不要因为一个小阻塞全部停摆。
6. **失败说人话**：超时、断网、Provider 限流、worker 崩溃要区分。
7. **Host 管权限**：Chief 的能力来自配置，不来自它自己的声明。
8. **本地真相**：任务、事件、转录、审批和项目关系以本地持久化记录为准。
9. **渐进自治**：先只读，再在项目中写，再允许 browser / Computer Use；不能一键从“聊天”跳到“整机 root”。
10. **可接管**：用户随时可以在 UI 接手、停止或检查 worker。

## 8. 非目标

第一版明确不做：

- Telegram 端的完整 IDE、文件管理器和模型设置中心；
- 多个用户共用一个 Chief 并做租户隔离；
- 多个具名 Bot 的群聊、人格市场或角色扮演；
- Chief 自己再创建 Chief，或任意深度递归 fan-out；
- 默认 always-approve、远程修改安全策略、远程读取系统凭据；
- 自动把改动 push 到远端、发布 Release、升级 Marionette；
- 让用户必须学习一套私有 DSL 或 MCP 工具名；
- 在电脑休眠、关机、断网或 Marionette 完全退出时假装任务仍能执行。

## 9. 产品验收标准

### 核心路径

- 用户只用自然语言即可开始一次远程代码任务，不需要发送 `/new` 或选择 session。
- Chief 能在 10 秒内确认已接单，并在任务启动后给出项目与 Agent 的选择理由摘要。
- worker 需要批准时，Telegram 收到可操作卡片；允许 / 拒绝与本地 UI 共享同一 waiter，先答先得。
- 用户可以说“停下”“把刚才那个改法换掉”“完成后把测试结果发我”，Chief 能对正确任务执行。
- 任务完成后，Chief 给出确定的结果摘要；即使 Chief Agent 临时不可用，Host 仍能看到 worker 的最终正文。

### 可靠性

- 主窗隐藏 / 最小化 / 贴边时，上述核心路径仍成立。
- Telegram 断网 30 分钟后恢复，不重复创建同一任务，不丢待处理用户消息。
- Marionette 重启后，任务状态与 Chief 对话可恢复；不把失联 worker 标成 completed。
- 任何“running”任务都有 heartbeat / freshness；超过配置阈值必须变成 stale / interrupted 并通知。

### 安全

- 未授权 chat、user 和 callback 一律拒绝。
- Chief 不能调用工具开放新项目根目录、修改自身权限或读取 DPAPI 明文。
- 项目外访问、系统设置、凭据、发布操作必须本地确认。
- 所有远程批准都能在审计记录中回溯到 task、worker、工具调用、请求内容和最终决定。

### 体验质量

- 典型任务不需要用户解释 Marionette 内部术语。
- 默认通知量低于现有“每个会话各自推送”，同一任务不会在手机里碎成十几段。
- 用户能看到当前用了哪个 Agent / 模型、是否在等自己、已花多久，以及最后交付在哪里。

## 10. 何时不该做这套功能

如果目标只是：

- 在一个固定的 OpenCode 项目里远程写代码；
- 不需要多 Agent、多项目、Council、Browser 或 Computer Use；
- 不需要把任务和本地 Marionette 会话统一管理；

那么直接使用成熟的单 Agent Telegram 客户端可能更轻。Marionette Chief 的价值来自多 Agent 壳、
跨用引擎和本地能力已经把“选择与编排”变成了真实问题；这时才值得把 Chief 做成产品。
